RN Chatbot Camera

A tiny React Native sample — chatbot + camera — built to learn the APK pipeline and sideloading onto a Chromebook

React Native Expo SDK 52 TypeScript Android APK

A deliberately small React Native app built with Expo: a single-screen chatbot that answers via local rules, plus a camera mode that captures pictures and drops them back into the conversation as image bubbles. The goal isn't the app itself — it's a clean excuse to walk through the full “code → APK → Chromebook” pipeline.

Goal

Answer three questions end-to-end:

  1. How do you scaffold a React Native app with camera access?
  2. How do you turn it into an installable .apk without owning a dedicated Android build machine?
  3. How do you sideload that APK onto a Chromebook?

Architecture

Expo's managed workflow is the right default for a learning project — it hides the Gradle / CocoaPods machinery behind a couple of CLI commands, and its cloud build service (EAS Build) produces a signed APK without needing Android Studio installed locally.

The App

Two modes, one screen state machine: chat or camera. No navigation library, no global state, no network calls.

// App.tsx — the whole thing
export default function App() {
  const [messages, setMessages] = useState<Message[]>(initialMessages);
  const [mode, setMode] = useState<'chat' | 'camera'>('chat');

  const appendMessage = useCallback((m: Message) => {
    setMessages((prev) => [...prev, m]);
  }, []);

  return mode === 'chat'
    ? <ChatScreen messages={messages}
                  appendMessage={appendMessage}
                  onOpenCamera={() => setMode('camera')} />
    : <CameraScreen onCapture={uri => { /* append image, switch back */ }}
                    onCancel={() => setMode('chat')} />;
}

The “bot”

Deliberately dumb. The point is the pipeline, not LLM integration.

export function respond(input: string): string {
  const q = input.trim().toLowerCase();
  if (/\b(hi|hello|hey)\b/.test(q))  return 'Hey there! How can I help?';
  if (/\bcamera\b/.test(q))          return 'Tap the camera icon to take a picture.';
  if (/\bapk\b/.test(q))             return 'Build one with `eas build --profile preview --platform android`.';
  if (q.endsWith('?'))               return "That's a good question — I'm just a demo bot.";
  return `You said: "${input}". Try asking about the camera or saying hi.`;
}

The camera

expo-camera v16 exposes a CameraView component and a useCameraPermissions hook. Everything you need for a shutter button fits in ~60 lines:

const [permission, requestPermission] = useCameraPermissions();
const cameraRef = useRef<CameraView>(null);

const takePhoto = async () => {
  const photo = await cameraRef.current?.takePictureAsync({ quality: 0.7 });
  if (photo?.uri) onCapture(photo.uri);  // bubble it back into chat
};

return <CameraView ref={cameraRef} style={{ flex: 1 }} facing="back" />;
Why expo-camera and not react-native-vision-camera? Vision Camera is more powerful (frame processors, GPU pipelines), but requires a development build and native config. For a learning project the managed workflow keeps the feedback loop short: edit, reload, done.

Permissions

The Android manifest needs CAMERA, and the Expo config plugin injects the user-facing consent string. Both live in app.json:

{
  "expo": {
    "android": {
      "package": "com.example.rnchatbotcamera",
      "permissions": ["android.permission.CAMERA"]
    },
    "plugins": [
      ["expo-camera", {
        "cameraPermission": "Allow $(PRODUCT_NAME) to access your camera to capture photos in chat."
      }]
    ]
  }
}

Building the APK

The fastest path: EAS Build. A cloud worker runs Gradle, signs the APK with a key it generates for you, and hands you a download link. No Android Studio, no JDK wrangling.

npm install -g eas-cli
eas login
eas init                              # links the project to your Expo account
eas build --profile preview --platform android

The preview profile is the interesting one — it's wired to emit an APK rather than an AAB (which is what Google Play actually wants but can't be sideloaded directly):

// eas.json
"preview": {
  "distribution": "internal",
  "android": { "buildType": "apk" }
}

Local build fallback

If you'd rather not depend on Expo's cloud (or you've hit the free tier limit), expo prebuild materializes the android/ project so Gradle can do the work on your own machine:

npx expo prebuild --platform android
cd android
./gradlew assembleRelease
# APK lands in android/app/build/outputs/apk/release/

That path needs JDK 17 and the Android SDK. EAS sidesteps both.

Installing on a Chromebook

ChromeOS runs Android apps inside a sandboxed Android subsystem (ARC). The Play Store is the official path, but for a sideloaded APK you go through ADB — the same protocol used for any Android device.

Two layers need to be enabled first:

  1. Linux (Crostini) — provides a shell where adb can run.
    Settings → Advanced → Developers → Linux development environment → Turn on
  2. ADB sideloading for ARC — opens the Android subsystem to adb install.
    Settings → Advanced → Developers → Linux development environment → Develop Android apps → Enable ADB debugging
Heads up: toggling ADB debugging on ARC shows a powerwash-style warning. In practice it reboots and keeps your data, but take a snapshot of anything irreplaceable first. You only need to do this once per device.

Then, from the Linux terminal

# 1. Install ADB once
sudo apt update && sudo apt install -y android-tools-adb

# 2. Move the APK into the Linux container
#    (drag it into "Linux files" in the ChromeOS Files app)

# 3. Point ADB at the Android subsystem — note the fixed IP
adb connect 100.115.92.2:5555
#    Accept the dialog that appears on the ChromeOS desktop

# 4. Install
adb install rn-chatbot-camera.apk

# 5. Launch it from the ChromeOS launcher
The magic IP: 100.115.92.2 is the address ChromeOS assigns to the Android VM. It's stable across reboots, so you can script this once and forget.

Things that tripped me up

Expo Go vs dev build

On SDK 52 with the New Architecture, some native modules (incl. some expo-camera paths) don't load inside Expo Go. A dev client build fixes it: eas build --profile development.

APK vs AAB

The default production profile builds an AAB, which Google Play can split per-device but ADB can't install directly. preview produces the APK you actually want for sideloading.

Package name clashes

com.example.* is fine for testing, but if you ever want to ship on Play you'll need a reverse-DNS package you actually own. Rename in app.json before the first store upload — it's effectively permanent afterward.

ARC ≠ a real phone

The ChromeOS Android runtime emulates a specific device. Sensors, camera APIs, and window resizing behave differently than a phone. Test the golden path on ARC and a real device before declaring victory.

What I learned

  1. Managed Expo is genuinely the path of least resistance for an Android-first learning project. The first signed APK was ~15 minutes from npx create-expo-app.
  2. EAS Build's preview profile is the one you actually want for sideloading. The default production path optimizes for Play Store distribution, which makes sideloading harder.
  3. Chromebooks are surprisingly good Android test targets. Once ADB is wired up, the feedback loop is as fast as a cable-attached phone, with the benefit of a full keyboard and a real debugger on the same device.
  4. The hardest part is the settings toggles, not the code. Both Crostini and ARC ADB live behind “Developers” menus that are easy to miss.
